# Demo mode Implementation Plan

> **For agentic workers:** follow `CLAUDE.md`: one builder for the whole plan (resume it for fixes), one Opus review at the end, nothing in parallel. Steps use checkbox (`- [ ]`) syntax.

**Goal:** `npm run demo` runs the real app with fictional sample data held in memory, with no Supabase calls, behind a "Demo mode" banner; the normal build and the live site are unchanged.

**Architecture:** The in-memory backend used by the tests moves into `src/lib/backend/memory.ts` and gains two demo-only options (a delay, and photos shown from the browser). `src/lib/backend/index.ts` chooses the demo backend when Vite runs in `demo` mode and the Supabase backend otherwise; because the choice is on `import.meta.env.MODE`, the production build drops the demo branch and its sample data.

**Tech Stack:** React 19, TypeScript, Vite (modes), Vitest + Testing Library.

**Spec:** `docs/superpowers/specs/2026-11-17-demo-mode-design.md`

## Global Constraints

- Project rules in `CLAUDE.md` apply: tests first; `npm test`, `npm run lint`, `npm run build` pass before every commit; only `src/lib/backend/` talks to Supabase; sample data fictional (`example.com` emails, 555-01xx phones if any).
- No change to `supabase/migrations/`, `.env`, `npm run dev` or the deploy workflow.
- A normal `npm run build` must contain no sample-student names and no demo banner text.
- Demo runs on port 5174 (`--strictPort`).
- Banner copy (exact): "Demo mode: sample data, nothing is saved. Refresh to start over." and, on a second line or after a separator, "Demo sign-in: demo@example.com · demo-pass1".
- Mobile-first; no horizontal scroll at 375 px; the banner never covers content.

## Review Focus

- A production build (`npm run build`) contains none of the sample names or the banner text, checked by searching `dist/`.
- The banner shows on Welcome and Set up your profile, which sit outside the shared page layout, as well as on every tab.
- At 1280 px the laptop results view (filters, list and map side by side) still fits the window with the banner above it: no page scroll added by the banner, map not stretched.
- In demo, creating a new pretend account goes to profile setup, a chosen photo appears on Account and in Students, and nothing is sent to the Supabase host.
- After a refresh the demo starts over: signed in as Demo Student, empty profile, no budget, no saved places.

**Sample data (`demoData.ts`):** 8 visible students (looking for roommates, with a name) and 2 hidden ones (switch off). Fictional names, `example.com` emails, a spread of programs (at least 5 different), years (including Graduate), move-in terms taken from `upcomingTerms(new Date())` so they never go stale, budgets across all four bands, and short bios (one at the full 300 characters, one empty). 5 of the visible students have illustrated avatars: inline SVG `data:` URIs (a coloured background and a simple drawn shape, no faces of real people, no outside image hosts); the rest show the initial circle. The visitor account "Demo Student" (`DEMO_EMAIL` / `DEMO_PASSWORD`) has an empty profile and empty state.

**Behaviour:**
- `package.json`: `"demo": "vite --mode demo --port 5174 --strictPort"`.
- `index.ts`: `defaultBackend` is `createDemoBackend()` when `isDemo`, otherwise today's Supabase backend. The Supabase client is not created in demo mode.
- `main.tsx`: in demo mode only, remove every `localStorage` key starting with `shp.` before the app renders, so a refresh starts over.
- `App.tsx`: render `<DemoBanner />` above the routes when `isDemo`, so it appears on every screen including Welcome and profile setup. It is in normal page flow (not fixed), slim, high-contrast, wraps on a phone. If the laptop results view relies on the window height, make it account for the banner so no page scroll appears.
- `README.md`: under "Run it", add `npm run demo` with one or two sentences: the app with sample students and no account or database needed, at http://localhost:5174, resets on refresh, sign-in shown on the banner.
